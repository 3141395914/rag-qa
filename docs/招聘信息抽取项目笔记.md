# 招聘信息抽取项目技术笔记

## 项目目标

把招聘网页批量整理成一张表格。输入是一批网页链接，输出是一个 CSV 文件，
每条记录包含公司、岗位名称、薪资、学历要求、工作地点五个字段。

## 整体流程

程序先判断网址类型。如果是国家大学生就业服务平台的 `corp.html` 企业页，
职位列表由 JavaScript 后加载，直接抓 HTML 只能拿到空壳，所以改为调用平台
的 JSON 接口，一次拿回结构化数据，不经过大模型。

其余页面走通用流程，分四步：抓取、抽取、校验、输出。

第一步抓取，用 requests 下载网页，再用 BeautifulSoup 删掉脚本、样式标签，
只保留正文文本。这一步决定了后面模型能看到什么内容。

第二步抽取，把正文和字段说明拼成提示词，发给 DeepSeek，要求它按 JSON 格式
返回结果。提示词里明确要求一页多岗位时全部抽出，不能只抽第一个。

第三步校验，把抽出来的每个字段回原文核对。核对办法是把值和原文都去掉空格
标点、统一小写，然后检查值里的数字和最长汉字片段有没有在原文出现过。
对不上就带着提示重新抽取，最多两轮。

第四步输出，把通过核对的 JSON 转成字典，多条结果写进一个 CSV 文件。

## 为什么一个页面要输出多行

招聘简章经常一页列了十几个岗位。第一版设计是"一个页面输出一行"，
结果只抽到第一个岗位。后来把提示词改成要求返回岗位数组，
输出时每个岗位单独一行，公司名这类页面级信息在每行重复填写，
这样表格可以直接排序筛选。

## 两层重试

项目里有两层重试，解决的问题不一样。

第一层是接口层。请求 DeepSeek 时偶尔会遇到 5xx 或者读取超时，
程序会等 1 秒重试，再等 2 秒重试，最多三次。接口失败是"没拿到结果"。

第二层是结果层。模型返回了结果，但某个字段在原文里找不到依据，
这时候带着"上次填的值和找不到依据"的提示重新抽取。结果不准是
"拿到了但不对"。两种问题的处理方式完全不同，所以要分开。

## 缓存

同一个网址跑过之后，抽取结果会存到本地 cache 目录，文件名叫网址的
MD5 哈希值。第二次运行时先查缓存，命中就直接读，不再调用模型。
缓存目录放在 .gitignore 里，不会被提交到仓库。

## 评测集

人工标注了 7 个页面、26 个岗位作为标准答案，存在 data/gold.json。
评测脚本按岗位名称把预测结果和标准答案对齐，再逐字段比对，
计算精确率、召回率和 F1。

第一版结果：精确率 78.8%，召回率 100%，F1 88.1%。

多抽出来的 7 个岗位全部来自同一个原因：页面底部有一个"相关职位信息"模块，
那是网站推荐的其他职位，不是这份简章招的岗位。据此改了两处：
清洗正文时从"相关职位信息"开始截断；丢弃没有岗位名称的空记录。

改进后精确率和召回率都是 100%，F1 100%。
样本规模只有 26 个岗位，这个结果只代表这批样本，
不代表任意网站都能做到这个水平，下一步要扩大样本量。

## 部分站点需要单独适配

通用流程靠模型理解页面，换网站不用改代码，这是项目的主体能力。

但有些站点的内容由 JavaScript 渲染，或者本身有现成的 JSON 接口。
这类站点要单独写适配器，因为各家接口的参数名、返回字段、分页方式都不一样。
例如国家大学生就业服务平台的职位接口，字段名是 jobName、degreeName、
salary、areaCodeName，换一个平台可能叫 position、edu、pay，
必须单独做字段映射。

当前只接了一个接口站点，所以没有提前抽象公共层。等出现第二个接口站点时，
再把适配器抽成统一的注册机制：每个适配器是一个函数，输入网址，
匹配就返回岗位列表，不匹配返回 None，主流程依次尝试。
