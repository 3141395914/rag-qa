# 本地文档知识库问答（RAG）

给一批本地文档建索引，问问题时先检索出最相关的几段，再把这几段和问题一起交给大模型回答，
答案后面标出依据来自哪段资料。

## 运行效果

```
$ python main.py ask "这个项目为什么要做结果校验？"
正在加载向量模型（第一次会慢一点）...
检索到的资料：
  [1] 相似度 0.440  招聘信息抽取项目笔记.md
  [2] 相似度 0.423  招聘信息抽取项目笔记.md
  [3] 相似度 0.398  招聘信息抽取项目笔记.md
  [4] 相似度 0.381  招聘信息抽取项目笔记.md

回答：
这个项目做结果校验，是为了确认模型抽取出的每个字段在原文里确实有依据，
防止"拿到了但不对"的情况。
具体做法是：把抽出来的每个字段回原文核对，核对办法是把值和原文都去掉空格标点、
统一小写，然后检查值里的数字和最长汉字片段有没有在原文出现过；对不上就带着提示
重新抽取，最多两轮[2][3]。
这属于项目里的"第二层重试"（结果层）...[1]
```

## 为什么要 RAG

大模型不知道你的私有文档。把整篇文档直接塞进上下文也有三个问题：文档太长塞不下、
token 成本高、上下文太长时模型注意力会被稀释，反而找不准重点。

RAG 的做法是先把文档切成小块存成向量，提问时只把最相关的几块交给模型。
这样既省钱，答案也有出处可查。

## 工作原理

**建索引阶段**：读文档，切成每块 300 字左右、相邻块重叠 60 字，
用 `BAAI/bge-small-zh-v1.5` 把每块转成一个向量，存到 `index/` 目录。

**检索阶段**：两路并跑。向量路把问题转成向量算余弦相似度；关键词路用 BM25 按字面词频打分。
两路结果用倒数排名融合（RRF）合并，取最相关的 4 块。

为什么要两路：向量擅长"意思相近"，但查型号、人名这类细节会模糊；BM25 擅长字面精确匹配，
但换个说法就找不到。两路互补。

**生成阶段**：把这几块和问题拼成提示词，交给 DeepSeek。提示词要求它只根据资料回答、
没有就说没提到、并用 [1] [2] 标出依据。

## 安装与运行

```bash
pip install -r requirements.txt
```

复制 `.env.example` 为 `.env`，填入 DeepSeek 的 Key。

第一次运行需要下载向量模型（约 100MB）。国内网络可以先设置镜像：

```bash
set HF_ENDPOINT=https://hf-mirror.com
```

把要问的文档放进 `docs/` 目录，然后建索引、提问：

```bash
python main.py index
python main.py ask "你的问题"
```

## 目录结构

```
config.py     模型名、切块参数、检索条数等配置
chunker.py    把长文档切成小块，切点尽量落在句号或换行处
embedder.py   加载本地向量模型，把文字转成向量
retriever.py  建索引、保存索引、按余弦相似度检索
bm25.py       关键词检索打分，补上向量检索的字面短板
generator.py  拼提示词，调用 DeepSeek 生成答案
main.py       命令行入口
docs/         放要检索的文档
index/        生成的索引，不进仓库
```

## 已知限制与下一步

- 目前只有一份文档、7 个块，规模太小，回答质量还体现不出检索的差距。
- 切块按固定长度切，没有按标题或语义切分，长文档里可能把一段完整论述切断。
- 只做了向量检索，没有重排序。工业界的做法通常是先向量召回一批，再用重排序模型精排。
- 没有评测。下一步可以准备一批问题和标准答案，测检索命中率和回答准确率。
- 向量模型跑在 CPU 上，文档量大时建索引会慢，后续可以换更小的模型或者加批处理。
